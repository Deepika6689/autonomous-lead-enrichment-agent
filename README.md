# Autonomous Lead Enrichment Agent

A Python agent that crawls public company websites (JS-rendered included),
cleans the content down to a token-efficient context, and uses an LLM
(Groq) with a strict Pydantic schema to extract structured company
intelligence — with deterministic, non-LLM guardrails against hallucinated
emails and LinkedIn URLs, and a documented, evidence-based confidence score.

## ✅ Status: tested end-to-end on real domains

Every module has been unit tested (`tests/test_extractors.py`, 10/10
passing) and the **full pipeline has been run live** against all three
target domains — postman.com, supabase.com, and vapi.ai — using real
Playwright crawling and real Groq API calls. All three succeeded.

**Actual run summary:**

| Domain | Status | Confidence | Leadership found | Emails found |
|---|---|---|---|---|
| postman.com | success | 0.90 | 4 (Abhinav Asthana - CEO, Ankit Sobti - CTO, Abhijit Kane, Kin Lane) | info@postman.com |
| supabase.com | success | 0.75 | 0 | abuse@, legal@, privacy@, security@supabase.com |
| vapi.ai | success | 0.70 | 1 (Jason Mitura - VP of Software Development) | none published |

Total cost for all 3 domains: **$0.008** (10,718 input / 2,161 output

LinkedIn URLs came back `null` for everyone above — this is expected, not a
bug. Company "about/team" pages rarely embed direct `linkedin.com/in/...`
links in the HTML itself; that's exactly the gap the optional Bonus 1 search
fallback (below) is designed to close, and it's off by default.

## Architecture

```
domains[]
  → Crawler (Playwright, headless Chromium): homepage + discovered internal pages
  → Page Discovery: same-domain link filtering (about/team/contact/pricing/etc.), capped
  → Content Cleaner: HTML → deduped, trimmed clean text (no raw HTML ever reaches the LLM)
  → Deterministic Extractors: regex email + LinkedIn URL candidates (source of truth)
  → LLM Client (Groq, JSON mode): structured extraction, given ONLY clean text + candidates
  → Pydantic validation: strict schema check, corrective retry on failure (final source of truth)
  → Hard backstop: any email/LinkedIn URL not in the candidate list is stripped, even if the LLM produced one
  → Confidence Scorer: rule-based score from concrete evidence (see formula below)
  → Result Builder: DomainSuccessResult or DomainErrorResult per domain (never crashes the run)
  → output.json
```

Each domain is processed independently and wrapped in a top-level
try/except in `enrichment_agent.py` — one domain failing (blocked, timeout,
empty content, LLM failure, etc.) never stops the others.

**Why no LangGraph:** evaluated and deliberately skipped. This pipeline is a
straight-line sequence of typed async steps per domain, with no branching,
looping, or multi-agent coordination that would justify the extra framework
weight. A plain `asyncio` pipeline is easier to debug, easier to explain in
a short demo, and has fewer moving parts to fail.

## Confidence Score Formula

Computed in `src/confidence.py`, entirely from evidence the pipeline
actually collected — never generated by the LLM. Weights sum to 1.0:

| Signal | Weight | Condition |
|---|---|---|
| `overview_present` | 0.20 | company_overview non-empty, ≥20 chars |
| `audience_present` | 0.15 | target_audience non-empty, ≥10 chars |
| `has_generic_email` | 0.20 | ≥1 generic business email found (contact@/sales@/etc.) |
| `has_leadership` | 0.15 | ≥1 leadership member with both name and role |
| `has_personal_linkedin` | 0.10 | ≥1 leadership member has a validated linkedin.com/in/... URL |
| `crawl_success_ratio` | 0.20 | (pages fetched successfully) / (pages attempted), scaled proportionally |

Final score = sum of the above, rounded to 2 decimals, clamped to [0, 1].
This rewards breadth of *actually found* evidence, and `crawl_success_ratio`
ensures a domain where most pages failed to load gets an honestly lower
score even if the little content retrieved happened to be rich.

## Anti-hallucination design (not just prompting)

Emails and LinkedIn URLs are found **before** the LLM ever runs, via regex
in `extractors.py`. The LLM is only asked to organize/attribute these
pre-found candidates — and `llm_client._enforce_candidate_backstop()` then
**strips any email or LinkedIn URL in the LLM's output that isn't in the
candidate list**, regardless of what the model produced. This was verified
directly (see below) rather than assumed from the prompt wording.

Personal vs. company LinkedIn URLs are distinguished at the regex level
(`/in/` vs `/company/`) and enforced again at the Pydantic model level — a
`LeadershipMember.linkedin_url` that doesn't contain `/in/` is silently
nulled by a field validator, so a company page can never end up attached to
a named person.

## Quick Start (Windows 11 / PowerShell)

```powershell
git clone https://github.com/Deepika6689/autonomous-lead-enrichment-agent.git
cd autonomous-lead-enrichment-agent

python -m venv venv
.\venv\Scripts\Activate.ps1

pip install -r requirements.txt
playwright install chromium

Copy-Item .env.example .env
# edit .env and paste in your real GROQ_API_KEY
```

Get a free Groq API key at https://console.groq.com/keys.

Run the agent:

```powershell
python -m src.main --domains-file domains.json
```

Or specify domains directly:

```powershell
python -m src.main --domains postman.com,supabase.com,vapi.ai
```

Output is written to `output/output.json`. Logs go to `logs/run.log` and
stdout.

Run the unit tests:

```powershell
pip install pytest
pytest tests/test_extractors.py -v
```

## Configuration (.env)

| Variable | Default | Purpose |
|---|---|---|
| `GROQ_API_KEY` | *(required)* | Your Groq API key |
| `GROQ_MODEL` | `openai/gpt-oss-120b` | Model used for extraction (Groq deprecated llama-3.3-70b-versatile for free/dev tier in Aug 2026 - this is its supported replacement) |
| `MAX_PAGES_PER_DOMAIN` | 8 | Cap on pages crawled per domain (homepage + internal) |
| `PAGE_TIMEOUT_MS` | 15000 | Playwright navigation timeout per page |
| `REQUEST_DELAY_SECONDS` | 1.0 | Delay between internal page fetches (politeness) |
| `MAX_RETRIES` | 2 | Extra LLM extraction attempts after schema validation failure |
| `ENABLE_SEARCH_FALLBACK` | false | Optional Bonus 1 - Tavily search for missing LinkedIn URLs |
| `TAVILY_API_KEY` | *(optional)* | Only needed if search fallback is enabled |
| `LOG_LEVEL` | INFO | Logging verbosity |

The project runs correctly with `ENABLE_SEARCH_FALLBACK=false` and no
Tavily key — the search fallback is a pure optional enhancement.

## Error Handling

Every domain resolves to one of two shapes in `output.json`:

```json
{"domain": "...", "status": "success", "company_overview": "...", "confidence_score": 0.75, ...}
```
```json
{"domain": "...", "status": "failed", "error_stage": "crawl_homepage", "error_message": "..."}
```

`error_stage` is one of: `crawl_homepage`, `content_extraction`,
`llm_extraction`, `unhandled`. Every failure is logged with a traceback in
`logs/run.log`; nothing fails silently.

Bot-protection pages are **detected and skipped**, never bypassed — no
captcha solving, header spoofing beyond a normal browser user-agent, or
proxy rotation is implemented, per design.

## Cost Tracking (Bonus 3)

Token counts (`input_tokens`, `output_tokens`) come directly from the Groq
API's `usage` field on each response — real numbers, not estimated.
`estimated_cost_usd` multiplies those real counts by a **documented,
hardcoded per-token price snapshot** for the configured model (see
`llm_client.py`), since Groq's API doesn't return a dollar figure directly.
This price should be re-checked against https://groq.com/pricing before
relying on it for real budgeting — it's an explicitly stated assumption, not
a fabricated number.
